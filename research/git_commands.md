# Git Command Deep-Dive



---

## 1. git squash

ملاحظة: squash مش أمر مستقل بذاته في Git — بيتنفذ عن طريق `git rebase -i HEAD~3` مثلاً (حيث العدد اللي بعد الـ HEAD هو عدد الـ commits من آخر واحد إلى عددهم).

**السيناريو:** عملت 3 commits أثناء ما كنت بعمل login، وقبل ما ارفع الشغل عايز أجمعهم في commit واحد مرتب. بعمل الأمر ده عشان يتجمعوا كلهم في commit جديد بتاريخ واحد نظيف.

## 2. git merge vs git rebase

الاتنين بيستخدموا لدمج تغييرات Branch مع Branch تاني، لكن merge بيحافظ على تاريخ الـ Branches بيخلي التاريخ خطي مستقيم ونظيف، بينما rebase بيعيد إنشاء الأساس بتاعه بحيث إنه يخلي الأساس بتاعه أعلى البرانش اللي عايز يتبني عليه، وبعدين أعمل rebase إنه يخلي الأساس بتاعه على آخر تعديل للـ main.

**السيناريو:** عندي feature Branch خلصتها وعايز أضمها لـ main؛ أستخدم merge لو عايز أحافظ على شكل التاريخ، أو rebase لو عايز تاريخ مرتب وخطي.

## 3. git help

بيجيبلك شرح أي أمر من أوامر Git وطريقة استخدامه.

**السيناريو:** نسيت أمر أو مش فاهم option بتاعه، فأستخدم `git help <command>` عشان أعرف أستخدمه صح.

## 4. git cherry-pick

بينقل commit معين من Branch لفرع تاني، من غير ما أدمج الـ Branch كله.

**السيناريو:** لقيت إن زميلي في Branch عمل commit فيه إصلاح مهم (bug fix)، فعملت `cherry-pick` له عشان أنقل الإصلاح ده لـ main بسرعة من غير ما أستنى باقي الـ branch.

## 5. git clean

أمر بيستخدم عشان يشيل الملفات اللي مش متتبعة (untracked). مثلًا لو كتبت `git clean -n`، هيروض الأول يعرّفني هو هيشيل إيه، وبعدين أعمل `git clean -fd`.

**السيناريو:** بعد ما بعمل build أو تجربة محلية، بيفضل عندي ملفات مؤقتة كتير في المجلد. بستخدم `git clean -n` الأول عشان أشوف هيشيل إيه، وبعدين `git clean -fd` عشان أنضف المشروع وأرجعه زي ما كان من غير الملفات دي.

## 6. git grep

الأمر `git grep "الحاجة اللي عايز تدور عليها"` والنتيجة إنه بيوريك كل الأسطر في كل الملفات اللي فيها الكلمة دي مع معلومات زي اسم الملف ورقم السطر. ممكن كمان نحط حاجة زي `-n` حيث ده رقم السطر اللي عايز يدور عليه في الملفات، و `-c` لو عايز تعدّ عدد مرات ظهور الكلمة.

**السيناريو:** لما بكون محتاج أعرف فين متغير أو دالة معينة مستخدمة في المشروع كله قبل ما أعدّل فيها، بستخدم `git grep` بدل ما أفتح كل ملف يدويًا، وده بيوفر عليا وقت كبير في المشاريع الكبيرة.

## 7. git blame

لما أكتب `git blame filename` بيطلعلي الملف سطر سطر، وجنب كل سطر مين اللي كتبه والتاريخ. لو عملت مثلًا `-L 10,20` هيظهرلي بس الأسطر من 10 لـ 20 في الملف ده.

**السيناريو:** لما بلاقي سطر كود غريب أو مش فاهم سببه في ملف ما، بستخدم `git blame` عشان أعرف مين من كتبه وفي أي commit، وده بيوصلني لرسالة الـ commit اللي بتشرح ليه اتكتب كده قبل ما أعدله أو أبعتش أي حاجة.

## 8. git bisect

بنكتب `git bisect start` عشان نبدأ الـ bisect، وبعدين نكتب `git bisect bad` يعني ظهرت المشكلة النهاردة، و`git bisect good v1.0` يعني كان شغال كويس عند الإصدار ده. وبعدين بيبدأ بيعمل أقل محاولات عشان نعرف الـ commit المسبب للمشكلة.

**السيناريو:** اكتشفت bug ظهر في وقت مش معروف بالظبط، فاستخدمت `git bisect` عشان يدوّر على الـ commit اللي سبب المشكلة بأقل عدد محاولات، بدل ما أفتش كل الـ commits يدويًا واحد واحد.

## 9. git shortlog

الأمر `git shortlog -sn` ده بيطلعلك عدد الـ commits لكل شخص مع اسمه، ومرتبين من الأكبر للأصغر.

**السيناريو:** احتجت أعمل تقرير سريع عن نشاط الفريق في المشروع، فاستخدمت `git shortlog -sn` عشان أشوف عدد الـ commits لكل شخص بشكل مرتب ومختصر، بدل ما أقرأ كل الـ commits واحد واحد.

## 10. git prune

`git prune` مش بيستخدم كتير لوحده، وده اللي بيستخدمه أكتر هو `git gc`، وده بيعمل تنظيف شامل (garbage collection).

**السيناريو:** بعد ما مسحت كذا branch مش محتاجه، استخدمت `git prune` عشان أنظّف البيانات القديمة اللي فضلت من الـ branches دي ومحدش بيستخدمها، عشان الـ repo يفضل نظيف.

## 11. git worktree

بنعمل `git worktree foldername name_of_branch`، وده بيعمله عشان تعزل الحاجات اللي ممكن تسبب مشاكل عن بعض، مثلًا على الـ feature الجديدة لوحدها، ولما أخلص تدخلها المشروع الأساسي وتمسح الـ worktree.

**السيناريو:** لما كنت شغال على feature ومحتاج أصلح حاجة عاجلة على main من غير ما أخبط في الشغل بتاعي، استخدمت `git worktree` عشان أفتح نسخة تانية من المشروع في مجلد منفصل، أصلح فيها المشكلة بسرعة وأرجع لشغلي الأصلي عادي.

## 12. git verify-commit

`git verify-commit <commit-hash>` — هيوريك تفاصيل التوقيع. لو التوقيع صحيح ومش موجود غلط، هيديك رسالة خطأ.

**السيناريو:** كنت محتاج أتأكد إن commit معين (زي تعديل في كود حساس زي الأمان) جاي فعلاً من موقّع بتوقيعه الرقمي ومحدش قدر يتلاعب فيه، فاستخدمت `git verify-commit` عشان أتأكد من صحة وهوية صاحب الـ commit قبل ما أدمجه.

## 13. git filter-repo

أداة حديثة (بديل موصى بيه رسميًا بدل `git filter-branch` القديمة) بتُستخدم لإعادة كتابة تاريخ الـ repository بالكامل — زي حذف ملف حساس من كل الـ commits اللي فيها، أو تغيير بيانات مؤلف معين في كل الهيستوري.

**السيناريو:** اكتشفت إن ملف فيه بيانات حساسة (زي كلمة سر أو API key) اترفع بالغلط في commit قديم من شهور، ومش كفاية إني أمسحه دلوقتي لأنه لسه موجود في تاريخ الـ commits القديمة. استخدمت `git filter-repo` عشان أشيل الملف ده من كل الـ commits في التاريخ بالكامل، وبعدها عملت force push ونبّهت باقي الفريق يعملوا clone جديد للـ repo عشان ماحدش يفضل عنده نسخة قديمة فيها البيانات دي.
